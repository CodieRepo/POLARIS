# POLARIS — Data Strategy

## 1. Evidence-Backed Hybrid Data Architecture
POLARIS implements a 4-layer hybrid data strategy that separates authoritative public records, scientific observation/reanalysis feeds, simulated operations, and derived analytical intelligence.

```
┌─────────────────────────────────────────────────────────────┐
│ Layer 4: Derived Intelligence                               │
│ (Risk scores, threshold alerts, recommendations, sims)      │
├─────────────────────────────────────────────────────────────┤
│ Layer 3: Simulated Operational Data                         │
│ (Asset status, inventory balances, shipments, maintenance)  │
├─────────────────────────────────────────────────────────────┤
│ Layer 2: External Real Scientific Data                      │
│ (Copernicus ERA5 reanalysis, NSIDC sea-ice, OSM maps)       │
├─────────────────────────────────────────────────────────────┤
│ Layer 1: Authoritative Real / Public Data                   │
│ (NCPOR / NPDC station baselines, geography, expedition refs)│
└─────────────────────────────────────────────────────────────┘
```

- **Layer 1: Authoritative Real / Public Data**: Official static and reference records sourced from NCPOR/NPDC, establishing ground-truth station positions, names, historical timelines, and public expedition histories.
- **Layer 2: External Real Scientific Data**: Real-world scientific feeds including ERA5 meteorological data, NSIDC sea-ice concentration records, and OpenStreetMap spatial tiles.
- **Layer 3: Simulated Operational Data**: High-fidelity operational models for asset conditions, inventory stock levels, personnel assignments, logistics shipments, and maintenance schedules.
  > **Mandate**: Simulated operational data is strictly labeled as synthetic/demo data and must **NEVER** be misrepresented as live telemetry or real Indian Antarctic Programme operational records.
- **Layer 4: Derived Intelligence**: Computed analytics, automated risk ratings, prescriptive recommendations, and scenario simulation projections generated by POLARIS analytical and intelligence modules.

---

## 2. External Data Integration Principles
- **Decoupled Architecture**: External APIs and data sources are never invoked directly within core business or domain logic.
- **Dedicated Adapters**: All external data access is routed through dedicated providers situated in `src/integrations/`.
- **Normalization Pipeline**:
  ```
  External Source ──► Adapter / Client ──► Validation & Normalization ──► Canonical POLARIS Model ──► Application / Domain
  ```
- **Boundary Isolation**: Application services and domain modules depend strictly on canonical POLARIS TypeScript types; they never consume raw third-party JSON payloads directly.

## 3. Verified Data Sources

| Source | Primary Role / Coverage | Data Products & Access Notes |
|---|---|---|
| **NCPOR / NPDC** | Official Indian polar research source | Station metadata, published meteorological observation reports. Certain datasets require authentication or manual request workflows; treated as an authoritative reference source rather than a hard runtime dependency for demonstrations. |
| **ERA5 (Copernicus CDS)** | Automated meteorological and climate feeds | Surface temperature, wind speed, precipitation, pressure, wave height. Treated methodologically as **atmospheric reanalysis**, distinct from in-situ real-time station sensors. |
| **NSIDC** | Polar sea-ice concentration and extent | **G02202 v6** for historical sea-ice climate data; **G10016 v4** for near-real-time sea-ice extent analysis and maritime route risk assessment. |
| **OpenStreetMap (OSM)** | Geospatial basemap and rendering layer | Base cartography and Antarctic coastlines. Follows tile usage policies with proper attribution; encapsulated behind map provider components. |

## 4. Seed Data Principles
- **Reference Seed**:
  - Official Indian research station baselines (Bharati, Maitri, Dakshin Gangotri, Himadri, IndARC).
  - Geographic coordinates, facility limits, operational seasons, and external data source registries.
- **Demo Seed**:
  - Realistic synthetic datasets representing active expeditions, equipment assets, inventory balances, cargo shipments, personnel rosters, and maintenance work orders.
  - Pre-configured simulation scenarios and risk triggers.
  - Clearly tagged and documented as simulated data for evaluation and demonstration purposes.
- **Ingestion Boundary**: External scientific feeds and dynamic datasets enter the system through dedicated ingestion scripts and pipelines, **never** via static database migration files.

---

## 5. Database Principles
- **Relational Integrity**: Enforce constraints strictly at the database level: primary keys, foreign keys with explicit cascade/restrict rules, `UNIQUE` constraints, `CHECK` constraints, `NOT NULL` fields, timestamp auditing (`created_at`, `updated_at`), and selective index optimization.
- **Controlled JSONB Usage**: Restrict `JSONB` storage to truly polymorphic or schema-flexible payloads (e.g., simulation configuration parameters, raw provider response snapshots, arbitrary alert payloads). Never use `JSONB` as a shortcut to bypass structured relational entities.
- **Minimal Complexity**:
  - **No PostGIS**: Standard decimal degrees (`lat`/`lng`) are sufficient for station and shipment locations.
  - **No Event Sourcing**: Use straightforward state tables paired with audit/transaction ledger tables (e.g., `inventory_transactions`).
  - **No Microservice Databases**: Single, coherent relational schema managed under a modular monolith.
  - **No Global Soft-Delete**: Avoid blanket `deleted_at` columns everywhere; use explicit state columns (e.g., `status = 'DECOMMISSIONED'`) where business lifecycles warrant it.
